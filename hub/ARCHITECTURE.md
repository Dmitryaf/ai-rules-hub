# Архитектура хаба правил

## Целевой результат

Целевой проект должен получить короткую локальную точку входа и читать только тот набор правил, который относится к его типу и текущей задаче.

```text
AGENTS.md целевого проекта
→ .ai-rules/RULESET.md с выбранными слоями
→ .ai-rules/PROJECT_RULES.md с локальной спецификой
→ .ai-rules/upstream/CORE.md
→ релевантные темы
→ выбранные профили
```

Хаб остаётся источником шаблонов и обновлений. Подключённый проект владеет локальными правилами, а выбранная копия переносимых правил обновляется явной локальной синхронизацией.

## Слои

### `rules/CORE.md`

Минимальные инварианты, применимые почти везде: контекст, scope, достоверность, источники истины, проверка, контроль владельца и честная передача результата.

Core должен оставаться коротким. Правило исключается из core, если оно требует конкретного типа продукта, данных, команды, платформы или режима обучения.

### Тематические `rules/*.md`

Подробные нормы для product, architecture/data, implementation, quality, security/privacy, documentation, Git/delivery, AI collaboration и research/evidence. Они подключаются по типу задачи.

### `profiles/`

Композиции для повторяющихся типов проектов. Профиль:

- ссылается на темы, а не копирует их;
- содержит только дополнительные обязательства;
- может сочетаться с другими профилями;
- не содержит временное состояние конкретного проекта.

### `templates/`

Стартовые формы локальных документов. Placeholder не является значением по умолчанию, а комментарий шаблона — нормативным правилом.

### `sync/` и managed-копия

`sync/catalog.json` задаёт разрешённые topics, profiles и их зависимости. Целевой `.ai-rules/manifest.json` выбирает состав, а `.ai-rules/lock.json` хранит revision и SHA-256.

```text
hub checkout + project manifest
→ plan
→ add / update / unchanged / conflict / orphan
→ explicit apply
→ .ai-rules/upstream/ + .ai-rules/lock.json
```

Синхронизация владеет только `.ai-rules/upstream/` и сгенерированным `.ai-rules/lock.json`. Корневой `AGENTS.md`, `.ai-rules/RULESET.md` и `.ai-rules/PROJECT_RULES.md` принадлежат проекту и после первичного seed не перезаписываются. Изменение upstream-файла после apply считается конфликтом, а не разрешением молча перезаписать проект.

### `hub/`

Продуктовые и архитектурные правила самого AI Rules Hub, provenance и решения о структуре.

### `hub/SOURCE_PROVENANCE.md`

Краткая карта происхождения правил и сознательно исключённой специфики. Полные исходные документы остаются в канонических проектах и подключаются только для временного read-only аудита.

## Разрешение конфликтов

Локальная специфика должна побеждать общий default, иначе правила нельзя применять к разным проектам. Но исключение записывается явно:

```md
## Исключение

- Исходное правило: ...
- Причина: ...
- Заменяющее поведение: ...
- Область действия: ...
```

Исключение не может молча отменить системное ограничение, безопасность среды или явно заданное требование владельца.

## Жизненный цикл правила

```text
наблюдение в проекте
→ evidence из канонического проекта
→ кандидат и проверка переносимости
→ профиль или тематическое правило
→ при подтверждении широкой применимости — core
→ уточнение, замена или удаление с migration note
```

Временный audit не продвигается напрямую в core. Сначала из него извлекается устойчивое решение, затем проверяется минимум на втором контексте или на фундаментальном риске вроде потери данных.

## Что пока не строится

- package registry правил;
- универсальная JSON/YAML-схема всех правил;
- сложная система rule IDs и dependency resolution;
- CI matrix для стеков подключённых проектов.
- remote fetch и автоматическое обнаружение проектов;
- массовый rollout и автоматическое разрешение конфликтов;
- автоматическое удаление orphan-файлов.

Эти возможности допустимы после реальных подключений, когда станут известны требования к rollout, конфликтам и pinning версий.
Конкретные условия старта отложенных направлений перечислены в [`BACKLOG.md`](BACKLOG.md).
