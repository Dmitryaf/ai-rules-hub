# Backlog AI Rules Hub

Документ фиксирует выполненный пользовательский интерфейс и направления, отложенные до пилотного подключения проектов. Порядок внутри приоритета не является обещанием реализации: каждая отложенная задача начинается после выполнения указанного условия.

## Выполнено

### Готовность диагностики к первому пилоту

Project doctor и status проверяют маршрутизацию выбранных profiles, RULESET сверяется только по секциям выбора, а dirty update preview явно отделяет рабочие файлы от базового commit SHA. Проверка хаба контролирует обратную полноту topic catalog; тесты закрепляют архитектурные инварианты без зависимости от точной редакции правил. Пользовательская документация описывает рекомендуемые сочетания profiles без новой schema и обязательного наследования.

### Содержательный аудит нормативного набора

Проведена классификация дублей, конфликтов scope, чрезмерно абсолютных и непроверяемых формулировок. Core сокращён до универсальных инвариантов; детализация перенесена в темы, профили оставлены с уникальными обязанностями, а композиция закреплена в каталоге.

### Адаптивный task playbook и эксплуатационная тема

`PROJECT_STUDY.md` сокращён до адаптивного read-only playbook без фиксированного каталога и набора файлов. Добавлена opt-in тема reliability/operations; она намеренно не включена в `standard-product`.

### Единый тонкий CLI

Реализован корневой `ai-rules.ps1` для `init`, `status`, `plan`, `apply`, `update`, просмотра каталога и проверки хаба. Он вызывает существующие initializer и sync-механизм; второго sync-движка, автоматического fetch и неявного Apply нет.

### Пользовательский onboarding и диагностика

Реализованы русскоязычный onboarding после `init`, заполнение выбранных профилей и тем в `RULESET.md`, проектный read-only `doctor`, итоговые темы с учётом профилей, описания каталога и документация полного пользовательского маршрута.

### Достоверность подключённого проекта

Реализованы точное определение отношения revisions через Git ancestry, независимая проверка managed snapshot по hash из lock, обязательная интеграция маршрутов pinned-проекта в `AGENTS.md`, предупреждения о расхождении manifest и `RULESET.md` и явное `Нет.` вместо необязательных placeholders.

## P1 — после пилотного использования CLI

### Транзакционность операций

Результат: ошибка записи не оставляет частично изменённый проект.

- Добавить полный rollback managed-файлов и lock для неуспешного Apply.
- Сделать initializer атомарным для manifest и seed-файлов.
- Сохранить текущие проверки конфликтов и запрет неявной перезаписи.

### Изменение состава правил через CLI

Результат: пользователь добавляет или удаляет профили и темы без ручного редактирования JSON.

- Добавить `configure` с операциями add/remove для profiles/topics.
- До изменения manifest всегда показывать read-only Plan нового состава.
- Не менять `RULESET.md` молча: предложить пользователю обновить причины и исключения.

### Удобный просмотр различий

Результат: пользователь видит содержательные различия для `update` и `conflict`, не разбирая только таблицу состояний.

- Добавить отдельный read-only `diff`.
- Не выполнять merge и не считать просмотр разрешением на Apply.

### Машиночитаемый вывод

Результат: автоматизация получает стабильный результат без разбора пользовательского текста.

- Добавить явный `-Format Json` для `status`, `doctor` и Plan-команд.
- Сохранить человекочитаемый русский вывод по умолчанию.

## P1 — после первого пилотного подключения

### Минимальный выпуск версий хаба

Результат: владелец проекта может выбрать понятную опубликованную версию хаба и связать её с полным commit SHA.

- Добавить компактный changelog изменений нормативных правил и sync-контракта.
- Определить правила release-тегов и migration note без отдельной сложной release-системы.
- Сохранить commit SHA и SHA-256 как фактическую основу воспроизводимости.

Условие старта: первый проект успешно прошёл первичный `Plan`/`Apply` и одно ручное обновление.

### Безопасная очистка orphan-файлов

Результат: проверенный orphan можно удалить явно, не затрагивая локально изменённые или неизвестные файлы.

- Сначала добавить отдельный план удаления.
- Требовать явный режим применения и проверку SHA-256 из lock.
- Никогда не удалять `orphan-modified` автоматически.
- Проверить входящие ссылки и сохранить обратимый путь восстановления.

Условие старта: реальные orphan-файлы появились минимум в одном подключённом проекте.

### Понятное разрешение конфликтов

Результат: пользователь видит source, managed-копию и локальное изменение и может вручную выбрать итог без автоматического merge.

- Добавить инструкцию или отдельный read-only diff-сценарий для `conflict`.
- Не перезаписывать managed-файл и не считать локальный текст новым общим правилом автоматически.
- После решения обновлять lock только через обычный `Plan`/`Apply`.

Условие старта: конфликт воспроизведён на пилотном проекте и текущей таблицы `Plan` недостаточно.

## P2 — после двух подключённых проектов

### Remote fetch через Git

Результат: пользователь может получить выбранную версию хаба без ручного переключения существующего checkout.

- Использовать обычный Git remote и точный commit или tag.
- Сначала показывать источник и revision, затем выполнять fetch с явного разрешения.
- Не связывать базовый механизм с GitHub API.
- Не запускать `Apply` автоматически после fetch.
- Рассмотреть явную команду получения выбранного tag или полного SHA, а не неявное обновление до latest.

Условие старта: ручное управление checkout стало повторяющейся проблемой минимум в двух проектах.

### Локальный реестр подключённых проектов

Результат: владелец видит, какие локальные проекты используют хаб и какие revision зафиксированы.

- Хранить абсолютные локальные пути вне публичного нормативного слоя хаба.
- Начать с read-only inventory и статуса.
- Не считать наличие записи разрешением изменять проект.

Условие старта: подключены минимум два проекта и ручной список перестал быть достаточным.

### Массовый аудит без массового Apply

Результат: одна команда строит независимый `Plan` для нескольких зарегистрированных проектов.

- Изолировать ошибки и результат каждого проекта.
- Не выполнять запись, commit или push в целевых проектах.
- Массовый `Apply` оставить отдельным будущим решением.

Условие старта: существует локальный реестр и одиночный `Plan` стабилен на двух проектах.

### Проверка доступности обновлений

Результат: пользователь вручную получает список проектов с более новой доступной версией хаба.

- Сначала реализовать явную read-only команду статуса.
- Фоновую проверку не добавлять до подтверждённой необходимости и решения о частоте, сети и уведомлениях.
- Не считать доступное обновление разрешением на его применение.

Условие старта: выпущено минимум две принятые версии хаба.

## P3 — только при подтверждённой необходимости

### Skills и workflows как отдельный слой

Результат: повторяющиеся task playbooks получают отдельный контракт только после подтверждения модели.

- Не менять schema из-за одного `PROJECT_STUDY.md`.
- Вернуться к решению после второго playbook, повторяемой потребности и проекта совместимой миграции.

Условие старта: существуют минимум два устойчивых playbook и каталог тем перестал достаточно выражать их подключение.

### Канонический frontmatter и генератор каталога

Результат: metadata правил генерирует каталог без двух источников истины.

- Сначала доказать, что ручная запись file, description и profile composition создаёт повторяющиеся ошибки.
- Не добавлять database, registry или classifier для локальной задачи генерации.

Условие старта: расхождение metadata повторилось минимум в двух принятых изменениях.

### Профиль operated-service

Результат: профиль добавляет только уникальные обязанности реально эксплуатируемого backend-сервиса.

- Пилотировать `reliability-and-operations` как отдельную тему.
- Не дублировать в профиле failure model, observability и recovery из темы.

Условие старта: backend-пилот выявил повторяющиеся обязанности сверх компактной темы.

### Тема AI-powered product

Результат: отдельные нормы появляются для реального продукта, где модель обрабатывает данные или влияет на пользовательский результат.

Условие старта: пилот выявил повторяемые риски model input, output, evaluation и user disclosure, которые не закрываются product, security и research.

### Отдельная тема performance

Результат: performance guidance отделяется от quality и reliability только при достаточном объёме самостоятельных норм.

Условие старта: компактных правил baseline, budget, capacity и regression недостаточно минимум для двух проектов.

### Провайдер GitHub API

Результат: GitHub API используется только для сценария, который нельзя надёжно закрыть обычным Git.

- До реализации назвать конкретное ограничение Git-подхода.
- Сохранить возможность локальной и автономной синхронизации.
- Не делать GitHub обязательной платформой хаба.

Условие старта: появился подтверждённый GitHub-specific сценарий.

### Альтернативные способы подключения

Результат: Git submodule или symlink рассматриваются только как документированная альтернатива для специального окружения, а не как новый default.

- Сравнить автономность checkout, Windows-совместимость, UX обновлений и риск случайной записи.
- Не заменять текущую manifest + lock + managed-copy модель без evidence пилотов.
- Не генерировать один общий гигантский `AGENTS.md`.

Условие старта: managed-копия не может закрыть конкретный воспроизводимый сценарий.

## Не планируется без отдельного решения владельца

- автоматический `Apply` сразу для нескольких проектов;
- автоматический merge конфликтующих managed-файлов;
- фоновое изменение проектов;
- автоматический commit, push, PR или release от имени владельца.
