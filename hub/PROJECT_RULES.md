# Правила развития AI Rules Hub

## Назначение

Хаб хранит проверенный, переносимый каркас правил для новых и существующих проектов. Его результат — не максимальное число инструкций, а небольшой непротиворечивый набор, который можно осознанно подключить, проверить и локально уточнить.

## Главный фильтр нового правила

Новое правило добавляется, только если понятны:

1. область действия;
2. риск или повторяющаяся проблема, которую оно предотвращает;
3. наблюдаемый способ проверки;
4. обязательность (`обязан`) или рекомендательный характер (`следует`);
5. допустимое исключение;
6. правильный слой: core, тема, профиль, шаблон, пример или provenance.

Если правило подтверждено одним доменом и несёт его терминологию, оно остаётся профилем либо проектным примером. Baseline не растёт из единичного предпочтения.

## Граница provenance

Полные dumps проектной документации не хранятся в хабе по умолчанию.

- Происхождение и границы обобщения фиксировать в [`SOURCE_PROVENANCE.md`](SOURCE_PROVENANCE.md).
- Канонический исходный проект подключать для аудита временно и read-only.
- Не считать локальный `AGENTS.md`, audit или roadmap универсальным правилом.
- Исправление правила исходного проекта и изменение производного правила — разные логические работы.
- Временную копию удалять после извлечения проверяемого provenance.

## Нормативная граница

Нормативны только:

- [`../rules/`](../rules/README.md) — универсальные правила;
- профиль, который проект явно выбрал;
- локальные документы самого проекта;
- для этого репозитория — настоящий файл и [`ARCHITECTURE.md`](ARCHITECTURE.md).

Шаблон, audit, source inventory и пример не становятся правилом без явного продвижения в нормативный слой.

## Изменение правил

При добавлении или изменении правила:

1. найти все дубли и противоречия в нормативном слое;
2. проверить канонические исходные документы и назвать provenance;
3. выбрать один канонический файл;
4. сформулировать правило независимо от исходного стека и домена;
5. обновить навигацию, профиль и шаблон только если их поведение реально изменилось;
6. обновить [`SOURCE_PROVENANCE.md`](SOURCE_PROVENANCE.md), если изменилось происхождение или граница обобщения;
7. выполнить проверки хаба.

Не копировать один и тот же нормативный абзац в несколько файлов. В профиле достаточно ссылки и дополнительных обязательств.

## Собственные ограничения хаба

- Основной язык нормативных документов — русский; общепринятый технический термин можно оставить на английском.
- Пути внутри репозитория — относительные Markdown-ссылки.
- В правилах нет команд конкретного package manager без пометки «пример» или профильной необходимости.
- Синхронизация управляет только allowlist-файлами внутри выбранного managed-каталога.
- `Plan` является режимом по умолчанию; `Apply` не перезаписывает локально изменённый managed-файл.
- Локальные `AGENTS.md`, `RULESET.md`, `PROJECT_RULES.md` и исключения не синхронизируются поверх проекта.
- Remote fetch, массовое обновление проектов и автоматическое удаление orphan-файлов пока не поддерживаются.
- Хаб не генерирует массово `AGENTS.md` и не переписывает правила других репозиториев без отдельного запроса владельца.
- Изменение manifest/lock schema требует compatibility-решения, теста и описания миграции.
- Существующие изменения пользователя и Git history сохраняются.
- Commit, push, release и публикация требуют отдельного разрешения.

## Готовность изменения хаба

Изменение готово, если:

- каноническое место правила однозначно;
- core не содержит профильной специфики;
- локальные ссылки проходят проверку;
- каждый imported Markdown-файл учтён в inventory;
- шаблоны не обещают несуществующую автоматизацию;
- sync plan не выходит за managed-каталог и корректно останавливается на конфликте;
- provenance соответствует фактическим источникам и не выдаёт временный audit за действующее правило;
- выполнены `scripts/check-hub.ps1`, `tests/test-tooling.ps1`, `git diff --check` и `git status --short`.
