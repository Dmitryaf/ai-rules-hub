# 0002. Границы правила, профиля и task playbook

Статус: принято.

## Проблема

Core, тематические правила и профили повторяли одни обязанности. Профиль одновременно объявлял композицию и добавлял уникальные требования, а большой `PROJECT_STUDY.md` задавал фиксированную структуру результата, язык и каталог для проектов любого размера. Из-за этого progressive disclosure зависело от нескольких расходящихся списков.

## Текущее состояние

Manifest выбирает профили и дополнительные темы. `sync/catalog.json` вычисляет effective-набор и sync копирует выбранный snapshot. Schema catalog остаётся `0.1`.

## Решение

1. `CORE.md` содержит только короткие универсальные инварианты.
2. Профиль содержит назначение и уникальные обязанности типа проекта; его композиция тем определяется только каталогом.
3. Выбранный профиль читается всегда, потому что именно в нём находятся обязанности, которые нельзя восстановить из тематических файлов.
4. Тематическое правило читается только когда effective-набор содержит тему и текущая задача относится к ней.
5. `PROJECT_STUDY.md` остаётся тематическим task playbook и подключается явно, а не через стандартный профиль.

## Почему профиль читается всегда

Профиль короток и задаёт действующие для проекта ограничения: например, границу публикации или жизненный цикл чувствительных данных. Если читать его только по типу текущего файла, эти обязанности можно пропустить до момента необратимого действия.

## Почему тема читается по задаче

Тематические документы подробнее и применимы к классу работ. Их чтение без связи с задачей увеличивает контекст и создаёт ложные обязанности, например эксплуатационный runbook для локального UI-прототипа.

## Почему `PROJECT_STUDY` остаётся темой-playbook

Он описывает способ выполнения отдельной задачи, а не устойчивый тип проекта. Компактный playbook допускает один или несколько выходных документов, следует языку и структуре целевого проекта и сохраняет источник read-only.

## Почему skills schema отложена

Один playbook не доказывает необходимость нового нормативного слоя, dependency model или изменения schema. Решение вернётся после появления второго playbook, повторяемой потребности отделить workflows и совместимого контракта миграции.

## Последствия

- Каталог является каноническим источником композиции профиля.
- Markdown профилей не содержит списков подключаемых тем.
- Routing читает профиль до релевантных тем и не загружает весь upstream.
- Добавление темы не требует schema migration, но требует каталога, навигации и sync-теста.
- `standard-product` не получает reliability/operations автоматически.

## Пересмотр решения

Решение пересматривается после второго устойчивого task playbook, пилота реально эксплуатируемого backend-сервиса либо доказанного ограничения catalog schema `0.1`.
