# Архитектура и данные

## Фактическое и целевое состояние

Архитектурный документ отдельно описывает:

- что реализовано сейчас;
- какие границы уже являются обязательными;
- что является целевым направлением;
- какие будущие модули пока не существуют;
- какие компромиссы приняты и когда их пересматривать.

Название будущего компонента в roadmap не означает решение создать его заранее.

## Источники истины

Для каждой категории данных фиксируются владелец, канонический источник, допустимые копии и способ синхронизации. Snapshot, cache и импортированное представление не редактируются как независимый второй источник.

При публикации внутренняя и публичная модели разделяются до UI. Публичная поверхность получает allowlist или отдельный publication snapshot и не фильтрует private-поля в компоненте.

## Границы доверия

- Входной JSON, backup, network response, message и данные внешнего API валидируются во время выполнения.
- Неизвестная версия формата даёт явную ошибку или поддерживаемую миграцию, а не частично правдоподобный результат.
- Нормализация завершает переход от legacy-формата к текущей runtime-модели; устаревшие поля не должны снова сохраняться без причины.
- Потерянное значение остаётся неизвестным. Adapter не подставляет ноль.
- Импорт заменяет данные только после успешной подготовки всего набора; для критичных изменений используется атомарность или безопасный rollback.

## Направление зависимостей

Обычное направление:

```text
внешняя среда
→ infrastructure adapter
→ нормализованная модель
→ domain/application rule
→ presentation model
→ UI
```

- Доменная логика тестируется без framework, сети, файловой системы и UI, где это возможно.
- UI координирует отображение и события, но не определяет доменные факты.
- Framework store является адаптером состояния, а не обязательным местом всей логики.
- Типы внешнего provider не распространяются на домен и публичный контракт.
- Integration side effects находятся за явной границей.

## Абстракции и миграции

- Общий модуль создаётся после как минимум двух реальных потребителей либо доказанной инфраструктурной необходимости.
- Архитектура развивается по одному наблюдаемому сценарию; работающий код не переносится массово ради одинаковых папок.
- Рефакторинг сохраняет поведение и формат данных либо содержит явную миграцию.
- Перед изменением смысла поля, единицы, диапазона или времени измерения определяется новая версия данных.
- Удаление legacy-пути защищается тестом совместимости или миграции.
- Необратимая миграция требует резервной копии, репетиции и условия отката.

## Состояния и ошибки

Проектировать реальные состояния: loading, empty, success, expected error, unavailable, stale, not-found и unknown — только там, где они действительно возможны. Не создавать фиктивный state ради checklist и не скрывать частичную ошибку успешным экраном.
