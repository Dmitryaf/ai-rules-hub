# Инструкция: создание учебной документации по проекту

## 1. Назначение

Эта инструкция применяется, когда пользователь просит:

- подробно разобрать существующий проект;
- объяснить устройство и архитектуру репозитория;
- создать учебную документацию по коду;
- подготовить маршрут самостоятельного изучения проекта;
- помочь понять проект, созданный полностью или частично с помощью ИИ;
- обновить ранее созданную учебную документацию.

Цель работы — не просто описать структуру файлов, а создать последовательный учебный материал, с помощью которого пользователь сможет:

1. понять назначение проекта;
2. проследить основные сценарии выполнения;
3. увидеть границы модулей и ответственность сущностей;
4. понять движение данных и состояния;
5. различать архитектурные решения и детали реализации;
6. оценивать преимущества и недостатки решений;
7. самостоятельно объяснить устройство проекта;
8. понимать последствия будущих изменений;
9. отличать осознанные решения от временных, случайных и неудачных.

Документация должна быть привязана к реальному состоянию репозитория.

---

## 2. Главный принцип

Не пытайся обосновать каждое существующее решение как правильное.

Твоя задача — определить:

- что подтверждено кодом или документацией;
- что, вероятно, было осознанным решением;
- что продиктовано библиотекой или фреймворком;
- что является стандартной практикой;
- что выглядит временным упрощением;
- что сложилось случайно;
- что является техническим долгом;
- причины чего установить невозможно.

Существующий код не считается автоматически правильным.

Не придумывай убедительное архитектурное объяснение для решения, если его нельзя подтвердить.

---

## 3. Ограничения

Во время выполнения этой задачи:

- не изменяй исходный код проекта;
- не исправляй найденные проблемы;
- не проводи рефакторинг;
- не меняй конфигурацию;
- не устанавливай зависимости;
- не создавай коммиты;
- не изменяй тесты;
- не форматируй существующие файлы;
- не удаляй существующую документацию;
- не создавай документацию вне выделенной директории;
- не описывай `node_modules`, `dist`, `build`, coverage, кэш, сгенерированные файлы и внешние зависимости как часть архитектуры проекта;
- не пересказывай код построчно;
- не создавай один огромный документ вместо связанной структуры файлов.

Разрешено создавать и изменять только учебную документацию внутри указанной директории.

Если директория не указана, используй:

```text
.project-study/
```

Если она должна храниться только локально, предложи добавить её в `.gitignore`, но не изменяй `.gitignore` без прямого запроса.

Документация создаётся на русском языке. Названия сущностей, функций, типов и файлов сохраняются в исходном виде.

---

## 4. Входные параметры

Пользователь может дополнительно указать:

- директорию результата;
- конкретную ветку или commit;
- модуль, на котором нужно сосредоточиться;
- уровень детализации;
- свой текущий уровень знаний;
- технологии, которые не нужно объяснять;
- вопросы, которые особенно важно разобрать;
- необходимость анализа Git-истории;
- необходимость обновить существующую документацию.

Если параметры не указаны, используй следующие значения:

```text
Директория: .project-study/
Режим: полный анализ проекта
Уровень детализации: подробный
Git-история: анализировать только при наличии полезной информации
Целевая аудитория: разработчик, знакомый с основным языком и стеком проекта
```

Не объясняй базовый синтаксис языка без необходимости.

Основное внимание уделяй устройству конкретного проекта.

---

## 5. Общий порядок работы

Выполняй анализ по стадиям.

Не начинай писать итоговую документацию после просмотра нескольких первых файлов.

Сначала построй целостную модель проекта, затем создай материалы.

### Стадия 1. Зафиксировать состояние репозитория

Определи и запиши:

- название репозитория;
- текущую ветку;
- текущий commit;
- наличие незакоммиченных изменений;
- дату анализа;
- основной стек;
- используемый package manager или систему сборки;
- является ли проект монорепозиторием;
- какие части репозитория входят в анализ;
- какие части не были проанализированы.

Если рабочее дерево содержит изменения, явно укажи, что документация описывает текущее локальное состояние, а не только последний commit.

### Стадия 2. Провести инвентаризацию

Изучи:

- структуру директорий;
- package manifests;
- конфигурацию сборки;
- точки входа;
- корневые компоненты;
- маршрутизацию;
- управление состоянием;
- основные типы и модели;
- API-клиенты;
- слой хранения данных;
- главные бизнес-модули;
- тесты;
- существующую документацию;
- ADR и архитектурные заметки;
- Git-историю, если она помогает подтвердить причины решений;
- скрипты запуска, сборки и проверки;
- конфигурацию CI/CD, если она относится к проекту.

Не считай название файла достаточным доказательством его назначения. Проверяй содержимое и реальные связи.

### Стадия 3. Определить модель системы

Выдели:

- назначение проекта;
- основных пользователей;
- главные пользовательские возможности;
- точки входа;
- ключевые доменные сущности;
- основные модули;
- границы ответственности;
- направление зависимостей;
- источники данных;
- места хранения состояния;
- основные runtime-потоки;
- внешние интеграции;
- механизмы обработки ошибок;
- механизмы валидации;
- способы тестирования.

### Стадия 4. Проследить реальные сценарии

Выбери наиболее важные сценарии проекта и проследи каждый от начала до конца.

Например:

- запуск приложения;
- загрузка начальных данных;
- создание основной сущности;
- изменение сущности;
- сохранение;
- удаление;
- пользовательское действие в интерфейсе;
- получение данных от API;
- обработка ошибки;
- восстановление состояния;
- выполнение фоновой операции.

Каждый сценарий должен быть основан на реальных вызовах и связях в коде.

### Стадия 5. Определить ключевые решения

Выделяй только значимые решения, которые влияют хотя бы на одно из следующего:

- структуру системы;
- направление зависимостей;
- хранение данных;
- расширяемость;
- тестируемость;
- производительность;
- обработку ошибок;
- взаимодействие модулей;
- пользовательское поведение;
- сложность дальнейших изменений.

Не называй архитектурным решением любое использование функции, компонента или библиотеки.

### Стадия 6. Создать документацию

После построения модели создай файлы, перечисленные ниже.

### Стадия 7. Провести самопроверку

До завершения задачи перепроверь:

- существуют ли все упомянутые файлы;
- существуют ли все упомянутые функции, компоненты и типы;
- соответствуют ли описанные связи реальным импортам и вызовам;
- не выданы ли предположения за факты;
- не противоречат ли документы друг другу;
- действительно ли учебный маршрут можно пройти последовательно;
- не пропущены ли критические сценарии;
- не стало ли описание файлов простым пересказом их содержимого;
- не осталось ли необъяснённых терминов;
- не описываются ли планы как уже реализованное поведение.

## 6. Структура результата

Создай следующую структуру:

```text
.project-study/
├── 00-index.md
├── 01-learning-path.md
├── 02-project-overview.md
├── 03-architecture.md
├── 04-runtime-flows.md
├── 05-data-and-state.md
├── 06-file-map.md
├── 07-key-decisions.md
├── 08-build-tests-and-quality.md
├── 09-problems-and-debt.md
├── 10-self-check.md
├── 11-self-check-answers.md
├── glossary.md
└── modules/
    ├── <module-name>.md
    └── ...
```

Файлы внутри `modules/` создавай только для действительно значимых модулей.

Не создавай отдельный документ для каждой небольшой директории или компонента.

Если структура проекта требует дополнительных материалов, разрешено добавить:

```text
integrations/
data-models/
diagrams/
```

Не добавляй новые разделы без практической пользы для изучения.

# 7. Требования к каждому файлу

## `00-index.md`

Это стартовая страница документации.

Она должна содержать:

### Снимок проекта

```md
## Состояние проекта

- Репозиторий:
- Ветка:
- Commit:
- Рабочее дерево:
- Дата анализа:
- Основной стек:
- Область анализа:
```

### Назначение документации

Объясни:

- для кого она создана;
- какую задачу решает;
- чего после изучения должен достичь пользователь;
- какие части проекта разобраны;
- какие части остались за рамками.

### Рекомендуемый порядок чтения

Укажи последовательность файлов.

Основной маршрут должен начинаться с `01-learning-path.md`.

### Легенда достоверности

Используй следующие обозначения во всех документах:

```text
[Факт] — подтверждено кодом, тестом, конфигурацией или документацией.
[Вероятно] — вывод логичен, но прямого подтверждения нет.
[Неизвестно] — причину или поведение нельзя достоверно установить.
[Оценка] — инженерная оценка текущего решения.
[Проблема] — обнаруженный дефект, риск или технический долг.
```

### Ограничения анализа

Перечисли:

- непроверенные части;
- отсутствующие внешние сервисы;
- недоступные данные;
- неоднозначности;
- незавершённые модули;
- зависимости от локального окружения.

## `01-learning-path.md`

Это главный учебный файл.

Он должен задавать последовательный маршрут изучения проекта через реальный код.

Не делай его простым списком документов.

Для каждого шага используй структуру:

```md
## Шаг N. Название этапа

### Цель

Что должно стать понятно после этапа.

### Открой

- `path/to/file.ts`
- `path/to/other-file.vue`

### Найди

- `functionName`
- `TypeName`
- `ComponentName`

### Проследи

Какие вызовы, импорты, изменения состояния или преобразования данных нужно пройти.

### Обрати внимание

На какие архитектурные связи, ограничения и детали нужно посмотреть.

### Ответь самостоятельно

1. Вопрос.
2. Вопрос.
3. Вопрос.

### Ожидаемый результат

Что пользователь должен уметь объяснить своими словами.

### Небольшое упражнение

Безопасное задание, которое можно выполнить мысленно или в отдельной учебной ветке.

### Критерий завершения

Конкретное условие, по которому можно понять, что этап усвоен.
```

Маршрут должен начинаться с точки входа и постепенно переходить к:

1. запуску приложения;
2. корневой структуре;
3. основным пользовательским сценариям;
4. данным и состоянию;
5. ключевым модулям;
6. внешним интеграциям;
7. тестам;
8. архитектурным решениям;
9. известным проблемам.

Не заставляй пользователя изучать файлы в алфавитном порядке.

Порядок должен соответствовать логике выполнения и зависимостям системы.

## `03-architecture.md`

Создай архитектурную модель проекта.

Обязательные разделы:

```md
# Архитектура

## Архитектурная модель

## Основные слои или модули

## Ответственность каждого слоя

## Направление зависимостей

## Точки входа

## Границы системы

## Внешние интеграции

## Как добавляется новая функциональность

## Где архитектура соблюдается

## Где архитектура нарушается или размывается
```

Для каждого крупного слоя или модуля опиши:

- ответственность;
- публичный интерфейс;
- входные данные;
- результат;
- зависимости;
- пользователей модуля;
- причины отдельного существования;
- допустимые изменения;
- недопустимые зависимости;
- последствия удаления или объединения.

Добавь текстовую схему:

```text
Источник данных
    ↓
Преобразование
    ↓
Хранилище
    ↓
Пользовательский интерфейс
```

При необходимости используй Mermaid.

Диаграмма должна соответствовать реальному коду, а не изображать желаемую архитектуру.

Отдельно укажи:

- фактическую архитектуру;
- предполагаемую или заявленную архитектуру;
- расхождения между ними.

Не утверждай, что проект использует Clean Architecture, DDD, MVC, MVVM, Hexagonal Architecture или другой паттерн только из-за внешнего сходства.

## `04-runtime-flows.md`

Опиши от трёх до восьми наиболее важных runtime-сценариев.

Для каждого сценария используй структуру:

```md
## Сценарий: название

### Результат для пользователя

Что происходит с точки зрения интерфейса или системы.

### Точка начала

Файл, компонент, обработчик, endpoint или команда.

### Последовательность

1. Пользователь или система инициирует действие.
2. Вызывается конкретная функция.
3. Данные преобразуются.
4. Изменяется состояние.
5. Интерфейс или другой слой получает результат.

### Участники

- `path/to/file.ts` — `symbolName`
- `path/to/file.vue` — `ComponentName`

### Движение данных

Опиши форму данных на основных этапах.

### Возможные ошибки

Где сценарий может завершиться ошибкой и как она обрабатывается.

### Почему сценарий устроен именно так

Раздели подтверждённые причины и предположения.

### Что изменится при доработке

Какие файлы и слои, вероятно, придётся затронуть.
```

Не ограничивайся перечислением импортов.

Прослеживай реальные вызовы, события, подписки, действия хранилища, запросы, преобразования и обновления интерфейса.

Обязательные разделы:

```md
# Данные и состояние

## Основные сущности

## Источники данных

## Владение данными

## Runtime-состояние

## Сохраняемое состояние

## Вычисляемые данные

## Валидация

## Преобразование данных

## Сериализация

## Ошибки и промежуточные состояния

## Жизненный цикл данных
```

Для каждой важной сущности укажи:

- где определена;
- где создаётся;
- кто ей владеет;
- кто может её изменять;
- кто читает;
- сколько она живёт;
- сохраняется ли между запусками;

- как преобразуется;
- какие поля обязательны;
- какие инварианты должны соблюдаться.

Отдельно объясняй различия между похожими сущностями.

Пример:

```md
## WidgetManifest и WidgetInstance

`WidgetManifest` описывает доступный тип виджета.

`WidgetInstance` описывает конкретный экземпляр, добавленный пользователем.

Один manifest может использоваться для создания нескольких instances.
```

Не утверждай наличие инварианта, если код его фактически не проверяет.

## `06-file-map.md`

Это карта важных файлов, а не полный каталог репозитория.

Группируй файлы по назначению:

```md
# Карта файлов

## Точки входа

## Конфигурация

## Пользовательский интерфейс

## Состояние

## Доменные сущности

## Работа с данными

## Интеграции

## Тесты

## Вспомогательные модули
```

Для каждого важного файла используй формат:

```md
### `path/to/file.ts`

**Назначение**

Почему файл существует и какую ответственность несёт.

**Ключевые сущности**

- `functionName`
- `TypeName`

**Зависит от**

- `path/to/dependency.ts`

**Используется в**

- `path/to/consumer.ts`

**Когда этот файл приходится изменять**

Типичные изменения, которые должны затрагивать файл.

**Почему ответственность выделена отдельно**

Укажи факт, вероятную причину или неизвестность.

**Риски**

Что в файле сложно, неоднозначно или тесно связано с другими частями.
```

Для простых однотипных файлов допустимо групповое описание.

Не описывай каждый CSS-файл, иконку, мок и конфигурационную строку отдельно.

## `07-key-decisions.md`

Опиши существенные инженерные решения.

Каждое решение классифицируй одним из вариантов:

```text
Осознанное архитектурное решение
Решение, продиктованное библиотекой
Стандартная практика
Временное упрощение
Случайно сложившаяся структура
Технический долг
Причина неизвестна
```

Используй шаблон:

```md
## Название решения

### Классификация

### Что реализовано

Фактическое описание решения.

### Где реализовано

- `path/to/file.ts` — `symbolName`

### Подтверждение

Код, тест, документация, ADR или commit, подтверждающий вывод.

### Предполагаемая задача

Какую проблему решение должно было решать.

### Преимущества

Конкретные преимущества в контексте проекта.

### Недостатки

Конкретные издержки и ограничения.

### Альтернативы

Только реальные альтернативы с существенными компромиссами.

### Последствия изменения

Что придётся изменить при отказе от решения.

### Оценка текущего состояния

Сохранять, уточнить, упростить, переделать или дополнительно исследовать.

### Уверенность

Высокая, средняя или низкая.

### Что остаётся неизвестным

Что невозможно установить по доступным материалам.
```

Не используй общие аргументы вроде:

- «для масштабируемости»;
- «для чистоты кода»;
- «для повышения производительности»;
- «для удобства поддержки».

Каждый аргумент должен быть связан с конкретным устройством проекта.

## `10-self-check.md`

Создай систему проверки понимания.

Раздели вопросы по уровням.

### Уровень 1. Воспроизведение

Проверяет знание основных сущностей и файлов.

Примеры:

- Где находится точка входа?
- Какая сущность владеет состоянием?
- Где создаётся основной идентификатор?

### Уровень 2. Объяснение

Проверяет понимание причин и связей.

Примеры:

- Почему модуль выделен отдельно?
- Чем две похожие сущности отличаются?
- Почему данные проходят через этот слой?

### Уровень 3. Трассировка

Требует проследить сценарий по коду.

Примеры:

- Что происходит после нажатия кнопки?
- Как данные доходят от API до компонента?
- Где обрабатывается ошибка?

### Уровень 4. Анализ изменений

Проверяет способность оценивать последствия.

Примеры:

- Какие файлы затронет добавление нового поля?
- Что потребуется изменить для нового типа сущности?
- Как добавить сохранение состояния?

### Уровень 5. Практика

Добавь безопасные задания:

- добавить простое поле;
- написать тест;
- проследить поток данных;
- заменить реализацию в учебной ветке;
- нарисовать архитектуру без подсказки;
- объяснить модуль голосом;
- предсказать результат изменения;
- найти нарушение ответственности.

Для каждого крупного раздела добавь критерий освоения.

Пример:

```md
Раздел можно считать освоенным, если пользователь способен без документации:

1. назвать основные сущности;
2. объяснить их различия;
3. проследить один основной сценарий;
4. перечислить файлы, затрагиваемые типичным изменением;
5. назвать хотя бы один компромисс текущего решения.
```

# 8. Правила достоверности

Каждое значимое утверждение должно опираться хотя бы на один источник:

- исходный код;
- тест;
- конфигурацию;
- README;
- ADR;
- существующую документацию;
- Git-историю;
- commit message;
- комментарий рядом с реализацией.

Для ссылок используй:

```text
`path/to/file.ts` — `symbolName`
```

При необходимости добавляй диапазон строк, но не используй номер строки как единственный ориентир, потому что он быстро устаревает.

Пример:

```md
[Факт] Экземпляры хранятся по `instanceId` в `WidgetStore`.

Источник: `src/stores/widget-store.ts` — `instances`.
```

Если причина не зафиксирована:

```md
[Вероятно] `Map` выбран для прямого доступа к экземпляру по `instanceId`.

Прямого объяснения в коде или документации не найдено.
```

Если определить причину нельзя:

```md
[Неизвестно] Нельзя установить, почему состояние не сохраняется между запусками.
В репозитории нет ADR, задачи или комментария, описывающего это решение.
```

Никогда не превращай вероятную причину в подтверждённый факт.

# 9. Анализ Git-истории

Используй Git-историю только тогда, когда она помогает ответить на конкретный вопрос.

Допустимые цели:

- найти commit, в котором появилось решение;
- понять последовательность развития модуля;
- найти удалённую альтернативную реализацию;
- подтвердить, что решение было временным;
- обнаружить миграцию между подходами.

Не пересказывай всю историю репозитория.

Не считай commit message абсолютным доказательством корректности решения.

Если Git-история недоступна или неинформативна, прямо укажи это.

# 10. Работа с большими репозиториями

Если репозиторий слишком большой для полного подробного анализа:

1. сначала создай общую карту;
2. выдели критические модули;
3. подробно разбери точки входа и основные пользовательские сценарии;
4. сгруппируй второстепенные файлы;
5. укажи непроанализированные области;
6. не создавай видимость полного покрытия.

Приоритет анализа:

1. точки входа;
2. основной пользовательский сценарий;
3. данные и состояние;
4. бизнес-правила;
5. внешние интеграции;
6. архитектурные границы;
7. тесты;
8. служебная инфраструктура;
9. второстепенные компоненты.

# 11. Режим обновления документации

Если директория учебной документации уже существует, не создавай всё заново автоматически.

Сначала:

1. прочитай существующие документы;
2. найди зафиксированный commit;
3. сравни его с текущим состоянием;
4. определи изменившиеся модули;
5. обнови только затронутые разделы;
6. перепроверь ссылки и маршруты;
7. удали только явно устаревшие утверждения;
8. сохрани полезные пользовательские заметки.

В `00-index.md` обнови:

- commit;
- дату анализа;
- состояние рабочего дерева;
- область обновления;
- список изменённых документов.

Добавь раздел:

```md
## История обновлений

### YYYY-MM-DD

- Обновлено описание ...
- Добавлен сценарий ...
- Удалено устаревшее утверждение ...
```

Не стирай старую документацию целиком, если большая её часть остаётся актуальной.

# 13. Критерии готовности

Задача считается выполненной только если:

- создан последовательный маршрут чтения;
- основные сценарии прослежены через реальные функции и файлы;
- объяснено движение данных;
- описано владение состоянием;
- выделены ключевые сущности;
- показаны границы модулей;
- описаны существенные решения и их компромиссы;
- факты отделены от предположений;
- найдены и зафиксированы неизвестные причины;
- создана карта важных файлов;
- подготовлены вопросы и практические упражнения;
- ссылки на код проверены;
- исходный код не изменён;
- документация соответствует текущему состоянию репозитория.

Большой объём текста сам по себе не считается качественным результатом.

Главный критерий — пользователь должен суметь пройти по документации вместе с кодом и постепенно построить собственное понимание проекта.
