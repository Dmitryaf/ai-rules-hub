# Переносимые правила

## Как читать набор

[`CORE.md`](CORE.md) обязателен для каждого подключённого проекта. Каждый выбранный профиль читается всегда: он содержит уникальные обязанности типа проекта. Тематические правила читаются только когда относятся к текущей задаче, даже если входят в композицию профиля.

Канонический состав профилей и порядок тем задаёт [`../sync/catalog.json`](../sync/catalog.json). Manifest выбирает состав проекта, а status показывает точный effective-набор.

| Документ | Когда обязателен |
| --- | --- |
| [`PRODUCT.md`](PRODUCT.md) | продуктовая функция, требования, UI-текст или приоритизация |
| [`ARCHITECTURE_AND_DATA.md`](ARCHITECTURE_AND_DATA.md) | модели, границы модулей, хранение, API, миграции |
| [`IMPLEMENTATION.md`](IMPLEMENTATION.md) | изменение кода, конфигурации или зависимостей |
| [`QUALITY.md`](QUALITY.md) | проверка и передача любого изменения |
| [`RELIABILITY_AND_OPERATIONS.md`](RELIABILITY_AND_OPERATIONS.md) | эксплуатация сервиса, деградация, восстановление или performance/capacity-риск |
| [`SECURITY_AND_PRIVACY.md`](SECURITY_AND_PRIVACY.md) | секреты, пользователи, личные данные, AI с инструментами, внешние сервисы, публикация |
| [`DOCUMENTATION.md`](DOCUMENTATION.md) | создание или изменение документации и рабочего контекста |
| [`GIT_AND_DELIVERY.md`](GIT_AND_DELIVERY.md) | ветки, коммиты, CI/CD, релиз или внешняя операция |
| [`AI_COLLABORATION.md`](AI_COLLABORATION.md) | распределение работы между человеком и AI, менторский режим |
| [`RESEARCH_AND_EVIDENCE.md`](RESEARCH_AND_EVIDENCE.md) | неизвестный API, исследование, эксперимент, аудит или доказательная рекомендация |
| [`PROJECT_STUDY.md`](PROJECT_STUDY.md) | явно выбранная задача создания или обновления учебной документации по существующему проекту |

Тематическое правило задаёт нормы для класса задач. `PROJECT_STUDY.md` дополнительно содержит инструкцию для конкретной исследовательско-документационной задачи, но не становится профилем и не подключается автоматически.

## Приоритет правил

При конфликте применяй следующий порядок:

1. ограничения среды, безопасности и явно заданная задача пользователя;
2. локальные правила целевого проекта;
3. явно выбранный профиль;
4. релевантные текущей задаче тематические правила;
5. `CORE.md`;
6. примеры и внешние подтверждения.

Более частное правило может уточнить процесс, команды и критерии. Ослабление защиты данных, достоверности, обратимости или контроля владельца должно быть явно названо, обосновано и согласовано; молчаливое исключение недействительно.

## Нормативный язык

- `обязан`, `нельзя`, `только` — обязательное ограничение;
- `следует` — правило по умолчанию, от которого допустимо отступить с записанной причиной;
- `можно` — разрешённый вариант, а не требование;
- пример не создаёт правило сам по себе.

Каждое новое правило должно отвечать на четыре вопроса: где действует, какой риск предотвращает, как его проверить и в каком случае допустимо исключение.
