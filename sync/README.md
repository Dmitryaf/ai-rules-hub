# Синхронизация правил с проектами

Версия `0.1` использует локальную pull-модель:

```text
checkout AI Rules Hub
→ выбранные topics и profiles
→ Plan
→ ручная проверка
→ Apply
→ автономная managed-копия в проекте
```

После `Apply` обычная работа проекта не требует доступа к хабу.

## Назначение файлов проекта

| Файл | Владелец | Назначение | Ручное редактирование |
| --- | --- | --- | --- |
| `.ai-rules-hub.json` | проект | Выбор `topics`, `profiles`, `destination` и revision хаба | да |
| `.ai-rules-hub.lock.json` | sync | Фактически применённые revision, состав и SHA-256 | нет |
| `.ai-rules/` | sync | Managed-копия только выбранных общих правил и профилей | нет |
| `AGENTS.md` | проект | Короткая точка входа и маршрутизация чтения | да |
| `RULESET.md` | проект | Композиция, исключённые правила и явные переопределения | да |
| `PROJECT_RULES.md` | проект | Архитектура, команды и ограничения конкретного проекта | да |

`AGENTS.md`, `RULESET.md` и `PROJECT_RULES.md` не должны копировать тексты общих правил. Профиль прежде всего выбирает тематические правила; дополнительные профильные обязательства остаются в одном файле профиля.

## Граница владения

- Хаб управляет только файлами под `destination`, перечисленными в lock.
- Изменённый вручную managed-файл получает состояние `conflict`; `Apply` останавливается и не перезаписывает его.
- Исключённый из manifest managed-файл получает состояние `orphan`, `orphan-modified` или `orphan-missing`. Версия `0.1` не удаляет orphan-файлы автоматически.
- Локальные `AGENTS.md`, `RULESET.md`, `PROJECT_RULES.md` и другие файлы проекта sync не перезаписывает.
- `Plan` ничего не записывает. `Apply` копирует только `add` и `update`, затем обновляет lock только при изменении его содержимого.

## 1. Первичное подключение проекта

Запусти из корня checkout хаба:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass `
  -File scripts/init-project-sync.ps1 `
  -ProjectRoot C:\path\to\project `
  -Profiles standard-product `
  -SeedProjectFiles
```

Команда:

- создаёт `.ai-rules-hub.json` с выбранным профилем;
- добавляет шаблоны `AGENTS.md`, `RULESET.md` и `PROJECT_RULES.md`, только если соответствующих файлов ещё нет;
- не создаёт `.ai-rules/` и lock;
- не запускает `Apply`.

Заполни placeholders в локальных файлах. В `RULESET.md` перечисли профиль, фактически подключённые темы из manifest и его профильных зависимостей, а также исключения. В `PROJECT_RULES.md` запиши только специфику проекта.

Сначала получи план:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass `
  -File scripts/sync-rules.ps1 `
  -ProjectRoot C:\path\to\project `
  -Mode Plan
```

Перед `Apply` проверь:

1. revision и признак `Hub dirty`;
2. destination;
3. что список `add` содержит только выбранный `CORE`, темы и профили;
4. отсутствие неожиданных `conflict`, `orphan` и `orphan-modified`;
5. что manifest и заполненный `RULESET.md` описывают одну композицию.

Применить проверенный план:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass `
  -File scripts/sync-rules.ps1 `
  -ProjectRoot C:\path\to\project `
  -Mode Apply
```

После первого `Apply` проверь diff проекта и выполни его собственные проверки. В проект следует коммитить `.ai-rules-hub.json`, `.ai-rules-hub.lock.json`, `.ai-rules/`, `AGENTS.md`, `RULESET.md` и `PROJECT_RULES.md`. Сам commit выполняется только с отдельного разрешения владельца.

## 2. Обычная работа в проекте

Хаб во время обычной разработки не нужен. Codex читает локальные `AGENTS.md`, `RULESET.md`, `PROJECT_RULES.md`, минимальный `.ai-rules/rules/CORE.md` и только относящиеся к задаче managed-темы.

- Общее правило не редактируется внутри `.ai-rules/`; оно изменяется в хабе.
- Обычная специфика проекта изменяется в `PROJECT_RULES.md`.
- Отступление от конкретного общего правила оформляется в `RULESET.md`.
- Каждое исключение указывает исходное правило, причину, заменяющее поведение и область действия.

## 3. Обновление общих правил проекта

1. Выбери проверенный commit хаба и получи его полный SHA:

   ```powershell
   git -C C:\path\to\ai-rules-hub rev-parse HEAD
   ```

2. Запиши все 40 символов SHA в `.ai-rules-hub.json`:

   ```json
   "source": {
     "repository": "ai-rules-hub",
     "revision": "0123456789abcdef0123456789abcdef01234567"
   }
   ```

3. Переключи локальный checkout хаба ровно на этот commit. Для pinned `Apply` checkout должен быть чистым.
4. Запусти `Plan` и проверь revision, summary и таблицу действий.
5. Просмотри diff версий хаба отдельно. `conflict` требует ручного решения; orphan-файлы проверь на ссылки и локальные изменения.
6. Запусти `Apply`.
7. Обнови композицию и дату принятия в `RULESET.md`, если выбор изменился.
8. Просмотри diff проекта и выполни его проверки.
9. Зафиксируй обновление правил отдельным проектным коммитом после явного разрешения.

`source.revision: null` пригоден для локальной подготовки: lock всё равно запишет фактический revision и `dirty`. Для воспроизводимого принятия правил используй полный SHA. `Apply` отклоняет неполный SHA, несовпадающий revision и pinned-обновление из dirty checkout.

## 4. Возврат локального правила в хаб

```text
локальное правило
→ подтверждение во втором контексте или фундаментальным риском
→ удаление проектной специфики
→ перенос в тематическое правило или профиль
→ фиксация происхождения в hub/SOURCE_PROVENANCE.md
→ проверка и выпуск commit хаба
→ явное принятие проектами через Plan и Apply
→ удаление локального дубликата
```

Если проекту после переноса всё ещё нужно уточнение, в нём остаётся только локальная добавка или оформленное исключение, а не копия общего текста.

## 5. Отмена неудачного обновления

Предпочтительный путь — откатить отдельный проектный commit обновления правил штатным Git-процессом проекта. Если новый commit ещё не зафиксирован:

1. верни в `.ai-rules-hub.json` предыдущий полный `source.revision` из истории проекта;
2. переключи checkout хаба на этот commit;
3. запусти `Plan` и убедись, что ожидаются только обратные `update`;
4. запусти `Apply`;
5. проверь diff и тесты проекта.

Если managed-файлы были изменены вручную, сначала сохрани или осознанно удали эти изменения: sync покажет `conflict` и не перезапишет их автоматически.

## Состояния Plan

| Состояние | Значение | Действие пользователя |
| --- | --- | --- |
| `add` | Managed-файла ещё нет | проверить, что файл выбран намеренно |
| `update` | Source изменился, локальная копия соответствует старому lock | просмотреть изменение правила |
| `unchanged` | Source и target совпадают | ничего |
| `conflict` | Managed-файл изменён локально или появился без подтверждённого lock | разрешить вручную до `Apply` |
| `orphan` | Файл больше не выбран и не изменён | проверить ссылки; автоматического удаления нет |
| `orphan-modified` | Исключённый файл изменён локально | сохранить решение вручную; автоматического удаления нет |
| `orphan-missing` | Исключённый файл уже отсутствует | проверить lock и ожидаемый состав |

## Краткая памятка

| Намерение | Где или как действовать |
| --- | --- |
| Хочу изменить общее правило | изменить хаб |
| Хочу изменить правило одного проекта | `PROJECT_RULES.md` |
| Хочу отступить от общего правила | `RULESET.md` |
| Хочу посмотреть обновление | `Plan` |
| Хочу применить проверенное обновление | `Apply` |
| Работаю над обычной задачей | использовать локальные правила проекта |

Версия `0.1` сознательно не выполняет remote fetch, массовое обновление проектов, merge конфликтов и автоматическое удаление orphan-файлов.
